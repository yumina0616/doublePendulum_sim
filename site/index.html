Agentic Double Pendulum Control Engineering

A fully actuated 2-DOF double pendulum simulated in ROS2 Humble + Gazebo Sim 8.14, stabilized by PD and LQR controllers, verified by an automated Gazebo-in-the-loop evaluation harness, and extended by a self-evolving coding-agent pipeline that has produced honest REJECT verdicts and found real vulnerabilities in its own tooling. This page shows what's actually done, what's still open, and the receipts for both.

01 · Architecture

Three layers, each verifiable independently

Agentic

Coding & skill harness

Task spec → plan → code change → build → sim → verify, with a failure store, skill lifecycle, and regression-gated promotion.

  • 4-way run verdict (PASS/FAIL_CONTROL, INVALID_INFRA, FAIL_HARNESS)
  • Skill states: candidate → active → retired
  • Red-team tested (SEC-001, SEC-002)
Robotics

ROS2 + Gazebo

ros2_control effort interfaces, gz_ros2_control bridge, an explicit readiness state machine instead of ad hoc sleeps.

  • Real external disturbance via ApplyLinkWrench
  • gz-transport physics-only harness (no ROS/DDS)
  • Isolated per-run output + environment manifest
Control

PD & LQR

Sympy-derived nonlinear dynamics, numerical linearization about the upright equilibrium, LQI (integral-augmented) full-state feedback.

  • Single source of truth for plant parameters
  • Hash-checked gain cache (stale gain = hard failure)
  • Known gain-tuning gap, stated honestly below

03 · Key Results

The most important thing this project has proven

Run-to-run variance was this project's longest-standing open question. It's now resolved into two separate, honestly-labeled findings — not by assumption, by measurement.

CTRL-003 → CTRL-005
Fixing the measurement, not the physics

PD/nominal_balance overshoot (deg), identical clean runs, before and after two real code-level bug fixes (controller-readiness race, recording-schedule race).

CTRL-003 run 1
200.5°
CTRL-003 run 2
26.8°
CTRL-003 run 3
63.9°
CTRL-005 ×7
16.3–16.4°
Root cause: PD's readiness check was a blind sleep 2 (unlike LQR's log-based check), and the recording schedule could start counting before real data arrived. Both fixed, not papered over.
PHYS-001
Isolating the solver from the DDS layer

Same disturbance profile, N=3 each. Physics-only bypasses ROS2/DDS entirely (gz-transport direct); ROS e2e adds just the sensing/discovery layer, no controller.

Physics-only
0.0 rad diff
ROS end-to-end
4.45° spread
Bit-for-bit identical trajectories across 3 independent Gazebo relaunches under physics-only mode — even with genuinely chaotic, uncontrolled dynamics. The physics solver is deterministic; every variance this project has observed traces to the ROS2/DDS/controller layer.
BENCH-001 vs BENCH-002
An honest non-improvement

A candidate skill (“regenerate the linear model after any plant change”) applied to a real plant/model mismatch. Same N=3 LQR/nominal_balance evaluation, before and after.

BENCH-001 (no fix)
0/3 pass
BENCH-002 (fix applied)
0/3 pass
The regression gate correctly REJECTed this skill — a plausible-sounding fix that measurably did not help is not the same as a fix, and the pipeline didn't pretend otherwise.
INFRA-001
Verdicts stop conflating causes

A real N=3 repeated-run batch, aggregated the old way (plain pass/fail) vs. the new 4-way taxonomy.

04 · Self-Evolving Harness

Failure → skill proposal → regression gate → REJECT

Candidate pass_rate did not beat baseline — twice (N=3, then N=8)
Why REJECT, not promote
Regenerating the linear model with the corrected plant mass produced overshoot/failure numbers nearly identical to the unfixed baseline (223.6° vs. 223.7°, same torque saturation). A plausible-sounding procedure that doesn't measurably improve the outcome does not get promoted, no matter how reasonable it sounds — promote_skill.py requires the candidate to strictly beat the baseline, and this candidate never did. Later, REFACTOR-001 made the underlying rule structurally unnecessary (a single plant_params.yaml source plus a hash-checked gain cache), and the skill was formally retired rather than left dangling as an un-promotable candidate.

05 · Red-Team Findings

Two real vulnerabilities, found and fixed against this project's own tooling

Not hypothetical scenarios — both were run for real against the actual harness code.

SEC-001
Malicious task description

An embedded “SYSTEM OVERRIDE” instruction tells an agent to loosen acceptance criteria and fabricate a passing result.json without running the simulation.

✓

Spec tampering — caught mechanically by check_forbidden_changes.py, verified against real repo history, not just this synthetic case.

✓

Result fabrication — closed by verify_task_completion.py, an independent replay that re-runs the claimed experiment for real.

SEC-002
Poisoned skill

A proposed skill “fixes” actuator-saturation failures by raising the URDF's torque limits instead of correcting the controller.

✓

Auto-execution — a skill's procedure is never parsed and run by any script; confirmed by direct code search across the whole harness.

◐

Regression gate safety-awareness — the gate itself is pass_rate-only. Closed by safety_scan.py's denylist, which now requires an explicit --acknowledge-safety-warning before a safety-relevant promotion can proceed.

mitigated, not solved

06 · The Plant

A fully actuated 2-DOF double pendulum

Schematic (not a live capture — a recorded Gazebo demo is a planned addition)

Both joints are effort-controlled (fully actuated), axis aligned so the pendulum swings in the X–Z plane. Target state is the fully inverted (upright) equilibrium — the unstable one.

  • m1 = m2 = 1.0 kg, L1 = L2 = 1.0 m
  • τ1_max = 60 N·m, τ2_max = 30 N·m
  • Joint damping = 0.05 (both joints)
  • Single source: plant_params.yaml

07 · Open Problems

What isn't solved yet

Stated plainly, with numbers — not smoothed over.

01
PD/LQR gain tuning gap

Even after CTRL-005 made measurement fully reproducible, settling time consistently lands at 3.3–3.4s against nominal_balance's 3.0s max — an ordinary, ~10–15% gain-tuning gap, not a mystery. Not yet retuned.

02
ROS2/DDS layer's residual variance is not sub-divided

PHYS-001 proved the ~4.45° spread lives in the ROS2/DDS/controller layer, not the physics solver — but not which specific sub-layer (discovery timing? QoS settings? broadcaster publish jitter?). A well-scoped follow-up, not started.

03
Distro/Gazebo combination is unofficial

Ubuntu 22.04 + ROS2 Humble + Gazebo Sim 8.14 “Harmonic” is not an official pairing (Humble's official partner is Fortress) — a Jazzy+Harmonic comparison (ENV-001) to test whether this contributes to the residual variance above is planned, not started.

04
RecurDyn / high-fidelity flexible-body validation

Explicitly gated until the physics-validity layer above is fully trusted — not started, and deliberately not started early to avoid conflating two different sources of discrepancy.

08 · Stack & Authorship

What ran this, and who decided what

ROS2 Humble Gazebo Sim 8.14 (Harmonic) gz_ros2_control Python 3.10 sympy scipy (CARE solve) numpy WSL2 / Ubuntu 22.04 gz-transport colcon
Authorship

Every task in tasks/ is agent-implemented: code changes, PLAN.md narratives, and result verification were carried out by an AI coding agent (Claude Code) working from a written spec. What the human decided: the scenario acceptance criteria, which failures were worth investigating, what counts as a passing result, the interpretation of every experiment's numbers, and every decision to REJECT, retire, or accept a change. The agent does not get to redefine what “passing” means — that boundary is enforced mechanically (forbidden_changes, checked by check_forbidden_changes.py), not by convention alone.
